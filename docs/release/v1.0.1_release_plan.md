## 2. Required public-history remediation (prepared, not executed)

Because the files were committed at `f75bc65` and have been present in
every commit since, **deleting them in a new commit is not sufficient** —
they remain retrievable from every prior commit in the public history.
Full remediation requires rewriting history to remove the blobs entirely,
which is a human-authorised, high-impact action (`force-push` required,
disrupts any existing clones/forks).

### Option A — `git filter-repo` (recommended if history rewrite is authorised)

```bash
# ON A FRESH CLONE, NOT THE WORKING REPOSITORY. Do not run against the
# author's primary working copy. Requires `pip install git-filter-repo`.
git clone --mirror https://github.com/MJabdelilah93/llm-dag-keyword-harmonisation.git repo-mirror
cd repo-mirror
git filter-repo --invert-paths \
  --path results/downstream_harmonisation_maps/raw_map.csv \
  --path results/downstream_harmonisation_maps/b3_map.csv \
  --path results/downstream_harmonisation_maps/full_llm_dag_map.csv
# Review the result thoroughly before proceeding.
# git push --force --all
# git push --force --tags
```

### Option B — BFG Repo-Cleaner (alternative)

```bash
# ON A FRESH --mirror CLONE, as above.
java -jar bfg.jar --delete-files "{raw_map.csv,b3_map.csv,full_llm_dag_map.csv}" repo-mirror.git
cd repo-mirror.git
git reflog expire --expire=now --all && git gc --prune=now --aggressive
# git push --force
```

**Neither command has been run.** Both require: a fresh mirror clone (never
the working directory), a force-push (rewrites public history — any
existing forks/clones will diverge), and explicit authorisation, since this
repair's ground rules forbid rewriting public history without it.

### Option C — Accept the exposure, document it, move forward (lowest-risk alternative)

Given the content (a harmonisation map derived from openly-licensed-search
Scopus author keywords, not full-text or abstracts) and that the same
content is already independently archived on a restricted Zenodo record,
the author/team may reasonably judge that a full history rewrite (with its
force-push disruption to any existing forks) is disproportionate. In that
case: remove the files going forward (done, this branch), document the
past exposure transparently (this file), and treat it as resolved without
history rewriting. **This is a judgement call for the authors, not made
here.**

  and why (referencing this repair), is the standard, low-risk way to ship
  corrections without disturbing anything already cited against v1.0.0.
